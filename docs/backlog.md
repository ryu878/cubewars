# Backlog

Non-blocking follow-ups and accepted design decisions carried forward across EPICs, so they don't get lost inside a single EPIC's task docs. Team Lead triages this when scoping future EPICs.

## Follow-ups (not yet scheduled)

- **Connection heartbeat / stale-connection cleanup** (from `docs/tasks/epic-04-infosec-findings.md`, F2). No WS ping/pong exists — a connection that dies without a clean `close` (dropped wifi, killed process, black-holed NAT) never gets cleaned up: registry/tracking-map entries leak, and the player keeps appearing in broadcasts, blocks hitscan, and auto-respawns forever as an uncontrolled "ghost." Fix: standard `ws` ping/pong pattern with `terminate()` on missed pong.
- **Max-connections cap / hitscan cost at scale** (from `docs/tasks/epic-04-infosec-findings.md`, F3). No cap on concurrent connections; `performHitscan` is O(n) per fire, so aggregate fire-processing cost is O(n²) in concurrently-firing players. Invisible at current (2-player) test scale — revisit deliberately when targeting higher concurrent player counts, don't force a fix now.
- ~~**Collision "corner pop" tightening**~~ — **done in EPIC 8** (`docs/tasks/epic-08-critic-review.md` F-001, `docs/tasks/epic-08-judge-verdict.md`). Root cause (square approximation of the circular player radius near box corners) fixed in `shared/src/collision.ts`; baseline/new-base speed worst-case overshoot cut ~4.6-10x (0.154m→0.015m, 0.204m→0.044m). **Residual, accepted as a known limitation**: at the new bunny-hop-boosted speed (~8.65 m/s), a single-tick worst-case overshoot of ~0.26m remains possible at genuine sharp physical outer-arena corners — independently verified (EPIC 8 Tester) as a single-tick, non-repeating, non-compounding artifact, not a sustained speed exploit, via a 200-tick oscillation test and a realistic multi-hundred-tick approach that showed zero overshoot under normal play. Fully eliminating it requires swept/continuous collision detection (a real architecture change, not a quick fix) — revisit only if this becomes a practical problem in real play, not preemptively. Reproducible via `npm run regression:collision-overshoot`.
- **Camera-at-spawn visual polish**: fixed in EPIC 4 (Task 7) for the FPS controller; no further action needed, noted here only for cross-reference.
- **No max-connections cap; spawn distribution designed/tested for ~6 concurrent players** (from `docs/tasks/epic-05-critic-review.md`). The arena's `SPAWN_POINTS` pool has 6 entries and the anti-clustering heuristic degrades gracefully but noticeably beyond that (a 7th simultaneous alive player can land within ~1.7 units of a neighbor — close to spawn-kill range). This is reachable by ordinary popularity, not just an adversarial test. Decide and implement one of: (a) cap concurrent connections at 6, or (b) add more spawn points / a bigger map if higher player counts are wanted.
- **QA evidence hygiene** (from `docs/tasks/epic-10-critic-review.md`, F-002). Some Tester QA runs leave stale/superseded screenshots (from a failed earlier attempt) alongside the corrected ones in the same `qa-artifacts/epic-NN-tester/` folder without flagging which is authoritative — not a product defect, but worth Tester deleting/clearly marking superseded evidence on future EPICs so the folder itself isn't ambiguous.
- **Remote-player footstep audio** (EPIC 14 "Procedural Sound System" Story 14.7, Design Decision 4 — `docs/tasks/epic-14-sound-system.md`). This EPIC ships LOCAL-player footsteps only (`client/src/fpsController.ts` `isRunning()` + `client/src/audio/soundManager.ts`'s cadence system). Hearing OTHER players'/bots' footsteps is deliberately deferred: it could in principle be inferred client-side from `WorldStateMessage` position deltas over time in `client/src/remotePlayers.ts` with no protocol change needed, but doing it well requires per-remote-player velocity estimation, deriving a believable cadence from noisy 20Hz position samples, and avoiding false-positive footsteps from server reconciliation snaps — real complexity on top of an EPIC that already spans jump/footstep/3-weapon-gunshot(local+remote)/4-pickup-category/hit-taken. Revisit as its own scoped story if remote footstep audio turns out to matter for gameplay feel in practice.

## Accepted design decisions (not bugs — document so they aren't "rediscovered" later)

- **`WorldStateMessage` broadcasts `position` and `health` for every player to every connected client**, unfiltered by distance or line-of-sight (from `docs/tasks/epic-04-infosec-findings.md`, F4). A client reading the WS feed directly (bypassing the renderer) gets persistent map-wide position/HP awareness of every opponent. `pitch` (aim direction) is correctly **not** broadcast, so exact aim-through-walls is not leaked. Accepted as a reasonable simplification for this game's current casual small-arena FFA scope. Revisit with per-recipient LOS/distance-gating if competitive integrity becomes a priority (e.g. ranked play, larger matches, anti-cheat-sensitive audience).
- ~~**Crates in the arena are full-height blocking obstacles, not climbable**~~ — **superseded by EPIC 12** (`docs/tasks/epic-12-jumpable-crates.md`). `MOVEMENT.jumpSpeed` raised (6 -> 7.5) so ballistic apex (1.5625m) clears `CRATE_HEIGHT` (1.2m); crates are now height-aware (`shared/src/collision.ts` `boxesBlockingAt()`/`crateTopHeightAt()`) — still block normally below their top, but support standing on top once mounted. Walls remain always full-height/non-climbable, unchanged.
- **Player hitboxes are an AABB approximation** (radius 0.5, height 2.2) of the rendered capsule, not a true capsule/cylinder intersection test (from `docs/tasks/epic-04-shooting-combat.md`). Accepted per the fixed stack's "no physics engine" constraint.
- **Mounting a crate requires releasing the forward key mid-jump, not holding it for the whole arc** (EPIC 12, `docs/tasks/epic-12-jumpable-crates.md`, discovered via `scripts/regression-crate-mount.ts`). At the current numbers (`MOVEMENT.maxSpeed` 13.3 m/s, `MOVEMENT.jumpSpeed` 7.5 m/s, `gravity` 18 m/s^2), a player's feet stay above `CRATE_HEIGHT` (1.2m) for ~0.40s of ballistic flight, which at max forward speed covers ~5.3m — more than any crate's radius-expanded footprint (<=2.8m). A literal "hold W and jump" the entire arc always overshoots every crate on this map; the real mount technique is approach-until-blocked, jump, and release forward roughly 350-500ms after the jump tick (a real, measured, non-frame-perfect ~150-250ms release window depending on crate size, not a single-tick window, since this game has no persisted air momentum — releasing forward mid-air simply stops horizontal drift). Accepted as-is for this EPIC (matches the spec's chosen "tune the existing ballistic jump" approach, not a new mantle mechanic); revisit only if playtesting shows this timing genuinely reads as unintuitive/undiscoverable rather than a normal "hop onto a ledge" feel.
