## Notes (non-blocking)

- **Bot facing-jitter-on-fire-tick (Tester's flagged concern #1):** confirmed by code read (`botAI.ts:230-237`) — the jittered yaw/pitch is applied via the same `applyInput()` used for normal smooth turning, so for the one tick a bot fires, its broadcast facing briefly reflects the jitter too, not just the hitscan ray. Judged **cosmetically negligible, not a real problem** — at ±0.05 rad (~3°) over a single 50ms tick at 20Hz this is imperceptible as a "snap," and arguably it's actually a *more honest* design than the literal spec reading: if only the ray were jittered while the bot's displayed facing stayed perfectly aimed, that would visually misrepresent what the bot just fired (it would look more precise than the shot it took). Reusing the single validated `applyInput()` entry point instead of adding a second, bespoke direct-field-mutation path for "cosmetic-only" yaw is also the better security/consistency posture per `security-baseline.mdc`. No action needed.
- **`AIM_JITTER_RAD=0.05` justification (explicitly checked, not just accepted):** the code comment (`botAI.ts:44-59`) ties the value to `PLAYER_HITBOX_RADIUS=0.5` (`shared/src/combat.ts:40`) via `atan(0.5/10) ≈ 0.05 rad` at a representative ~10-unit engagement range — I verified this arithmetic independently (`atan(0.05) ≈ 0.04996 rad`, matches) and re-ran the regression script myself, getting a sensible curve (100%/100%/41%/21% at 3/10/20/30m) consistent with that reasoning. This is genuine, checkable tuning justification, not a blind accept of the Team Lead's suggested starting number — no red flag.
- **Architecture soundness beyond the Tester's straight-on/corner tests:** independently stress-tested `resolveSteppedMovement()` with a standalone probe script exercising (a) near-tangent grazing angles along a flat wall (0.1°-5° off pure-tangent) at boosted speed, and (b) artificially large `dt` values (0.5s/2s/10s — none of which the server actually produces, since `TICK_DT_SECONDS` is a fixed constant per `server/src/match.ts:44`, not measured wall-clock elapsed time, so a stalled event loop cannot inject a dt spike into physics; confirmed by code read). In every case the wall was never crossed — the safety property (`totalDistance/stepCount ≤ maxStepDistance`, always, by construction of `stepCount = Math.ceil(totalDistance/maxStepDistance)`) holds independent of speed or dt, not just at the specific figures the committed regression script happens to sweep. This is genuinely robust engineering, not numbers tuned to pass a specific test.
- **Performance:** worst case at the new top speed is `Math.ceil(0.865/0.4) = 3` sub-steps per player per tick (unboosted: 2), each sub-step sweeping ~22 `ARENA_GEOMETRY` boxes × 3 resolution passes — a few hundred cheap AABB checks per player per 50ms tick. Trivial at this player/bot count; no performance concern.
- **Client/server desync risk:** both `stepPlayer()` and `fpsController.ts`'s prediction call `resolveSteppedMovement()` with no `maxStepDistance` override in either call site (confirmed by reading both call sites directly) — both fall through to the same `DEFAULT_MAX_STEP_DISTANCE` constant, so there is no way for the two to drift on this parameter. No new rubber-banding risk introduced.
- The redundant-double-run pattern in `scripts/regression-bot-aim-miss-rate.ts` (it runs 3m/10m/20m/30m once for the printed table, then re-runs 3m and 30m again independently for the pass/fail gate, so the two "3m"/"30m" numbers shown can differ slightly run-to-run) is a minor script-quality nitpick, not a correctness issue — both are large-N (200 attempts) independent samples of the same real distribution. Not worth a finding.
